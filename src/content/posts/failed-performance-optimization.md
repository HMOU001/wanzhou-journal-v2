这是一次失败的复盘。技术上的每一步都堪称教科书，结果上它几乎没有产生任何业务价值。把它写出来，是因为这种失败比成功更难看到有人讲。

## 背景

今年四月，我负责的活动页被点名：Lighthouse 性能分 58，LCP 3.1 秒。优化目标很明确，手段也都是标准动作。两周后上线：LCP 1.9 秒，性能分 91，团队周会上还展示了一下。

一个月后看数据：跳出率没变，转化率没变，停留时长没变。

## 我们做了什么

技术上没有偷懒，列出来都是常规正确项：

- 首屏大图从 1.2 MB 压到 210 KB，换了 AVIF，加了 `fetchpriority="high"`
- 三个第三方脚本改成延迟加载，其中一个直接删了
- 字体子集化，从 380 KB 降到 46 KB
- 关键 CSS 内联，其余异步

```
LCP   3.1s  →  1.9s
INP   280ms →  120ms
CLS   0.18  →  0.02
```

数字漂亮，体验也确实快了。那问题出在哪？

## 两个月后想明白的事

复盘是在六月的季度总结里被迫做的。结论有三条，按疼痛程度排序：

> 我们优化的是「页面加载」，用户在意的是「事情办成」。这两件事的相关性，没有性能布道者说的那么强。

第一，这个页面的流量大头是活动期内投放带来的，用户意图极强——他们就是来报名的，3.1 秒也等得起。第二，真正拖垮转化的是报名表单本身，七个字段、两个必填的验证码，这一步的流失率是加载阶段的四倍。第三，性能分是团队的指标，不是用户的指标。

性能优化当然是对的。但它排在表单简化后面，而我们先做性能，是因为它更好做、更好量化、更好展示。

## 现在的规矩

这以后我给自己立了一条规矩：任何优化动工前，先回答「用户在哪个环节真的被卡住了」。如果答案来自猜测而不是数据，那就先去拿数据，哪怕拿数据这件事本身要花一星期。

快是好的。但快不是目的，是手段——这句话人人都说，轮到排期时人人都忘。
